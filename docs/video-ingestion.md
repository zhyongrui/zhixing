# 哔哩哔哩与抖音视频入库流程

本文用于知行地图的地点视频入库。每条视频都要经过「核实视频与地点 → 取得完整卡片信息 → 查重 → 写入 → 在公开接口和手机上复查」。账号批量分析也按同一标准逐条处理。

当前 iOS 仓库只包含客户端；生产地点、外链和管理接口仍由已有服务提供。服务地址与管理凭证以受控部署配置为准，不要把它们写进仓库，也不要把客户端的 `APP_API_BASE` 当成管理后台地址。

## 发布标准

一条视频只有同时满足以下条件才算完成入库：

1. 原视频可打开，确认是目标作者、目标内容，且有明确地点证据。
2. 使用视频的标准 HTTPS 地址：哔哩哔哩 `https://www.bilibili.com/video/BV.../`；抖音 `https://www.douyin.com/video/<数字 ID>`。
3. 标题是可读的纯文本；作者昵称与视频所属平台一致；真实封面是可访问的 HTTPS 图片。
4. 地点名称、层级、父级和地图坐标正确；没有重复地点或重复视频。
5. 公开地点详情返回这些字段，手机上的卡片能显示封面和作者，点击能打开对应视频。

接口虽然允许 `creatorName` 和 `thumbnailUrl` 留空，日常发布不能因此省略。当前 iOS 会尝试在线补取哔哩哔哩视频的封面和作者；抖音没有这个补取逻辑，缺封面就会显示默认图标。为了让两种平台的卡片稳定一致，**两个平台入库时都填写作者与封面**。拿不到可信封面时先记为待处理，不要把默认图标当作完成状态。

## 1. 建立候选清单

从博主主页分析「所有视频」时，先逐页收集可见作品，记录主页显示的作品数、实际取得的作品数和检查日期。逐条建立工作记录，不要只凭搜索结果或第一页就宣称全部分析完成。推荐记录以下字段：

| 字段 | 记录内容 |
| --- | --- |
| 视频 | 原始分享链接、标准地址、BV 号或抖音数字 ID |
| 内容 | 原标题、作者、平台、发布时间（能取得时） |
| 地点 | 候选地点、精度（省/市/景区/具体 POI）、证据出处 |
| 处理 | 待核实 / 已入库 / 不适合 / 链接失效、原因、地点 ID 与外链 ID |

标题、简介、视频画面与讲述、字幕、地点标记、评论可以互相印证。**账号归属地、相似风景、泛泛的旅行标签、单条未经核实的评论不足以确定地点。** 用户明确指出视频地点时也要核对链接确实指向所说的视频。只有一个宽泛区域能确认时，关联那个区域；能确认具体酒店或景点时，优先关联具体地点。跨多地的路线视频可以建明确的路线地点；不要为了多放几个地图点而猜测途经地点。

无法确定的视频保留在待核实清单，写明缺少什么证据；失效、私密或 404 的链接单列，不入库。一个视频跨平台重复发布时先比较内容，按用户对该博主的既定平台偏好保留或替换，避免同一地点出现重复卡片。

## 2. 取得标准视频地址

- 哔哩哔哩：打开 `b23.tv` 等短链接，取得最终 BV 号，保存 `https://www.bilibili.com/video/BV.../`。去掉分享追踪参数。
- 抖音：打开 `v.douyin.com` 短链接，取得最终 `/video/<数字 ID>`，保存 `https://www.douyin.com/video/<数字 ID>`。短链接和搜索页链接不要直接入库：当前 iOS 依赖抖音域名路径中的 `/video/<数字 ID>` 提取 ID，标准长链接可让它优先唤起抖音 App。
- 核对跳转后的 ID、视频标题和作者与原分享内容一致。跳转到首页、搜索页、登录页或其他作品时停止入库。

查重以平台视频 ID 为主，不能只比原始 URL；同一视频的短链接和带参数的长链接可能不同。管理后台「外链」总览能查看全量链接。现有外链表没有 URL 唯一约束，重复入库需要在写入前主动排除。

## 3. 取得标题、作者和真实封面

### 哔哩哔哩

优先从视频详情取得 `data.title`、`data.owner.name`、`data.pic`，当前客户端使用的详情接口是：

```text
https://api.bilibili.com/x/web-interface/view?bvid=<BV号>
```

确认响应 `code == 0`、BV 号与目标一致，再使用这些字段。封面若以 `http://` 开头，换成可用的 `https://` 地址并验证图片。接口失败时打开原视频页核对，不要用搜索摘要猜作者或封面。

### 抖音

先用标准视频地址在浏览器中打开，核对页面标题、作者和视频 ID。抖音普通 `curl` 可能只返回反爬脚本；上次遗漏封面正是因为停在了这一步。当前浏览器渲染后的页面提供 `lark:url:video_cover_image_url` 元数据，可用于取得封面。例如在装有 Microsoft Edge 的 Mac 上：

```sh
"/Applications/Microsoft Edge.app/Contents/MacOS/Microsoft Edge" \
  --headless=new --no-first-run --disable-gpu \
  --user-data-dir=/tmp/zhixing-douyin-meta \
  --dump-dom 'https://www.douyin.com/video/<数字 ID>' \
  > /tmp/zhixing-douyin.html
```

检查生成页面的 `link[rel=canonical]`、`title`、`meta[name=description]` 和 `meta[name="lark:url:video_cover_image_url"]`。封面地址中的 HTML 实体要解码，例如把 `&amp;` 还原为 `&`。页面若仍只有验证脚本、没有目标 ID 或元数据，就换正常浏览器核实或保留待处理；不要拿其他视频、博主头像或自制图片冒充封面。

两个平台都需要在保存前对封面 URL 发起 HEAD 或小范围 GET，确认返回 2xx 且 `Content-Type` 是图片，并在浏览器中查看图片确实属于该视频。抖音图片可能是带 `x-expires` 的签名 URL：检查到期时间；临近到期或返回 403 时重新取封面。不要把 `&amp;`、搜索高亮标签、验证码页面地址当成图片 URL。

**标题必须是纯文本。** 取原视频标题或文案的主要内容，去掉“复制打开抖音”等分享说明和无关的推广标签，不改动地点与内容事实。搜索结果可能把命中词包在 `<em class="keyword">...</em>` 里；优先使用视频详情原题。若只有带高亮标签的摘要，去除标签并解码 HTML 实体后，还要和原视频核对。崇明岛等 5 条卡片曾因直接保存搜索结果标题而在 iOS 显示 `<em class`，这类内容不能通过发布检查。

## 4. 确认地点和坐标

先在管理后台「地点」按名称及别名搜索，再比对地图位置，避免把同一酒店、景点建成多个地点。选择与视频证据匹配的最具体层级：省、市、区县或 POI。具体酒店应定位到酒店，不用城市中心代替。

新地点优先在管理后台用高德地图搜索、选点或拖动图钉。地点库的 `Place.lat/lng` 统一采用 **GCJ-02**，顺序是 `lat, lng`；高德地图组件返回 `[lng, lat]`，写入时不要颠倒。GPS、EXIF、Core Location 等 WGS-84 来源需要先转换成 GCJ-02，再与地图核对。不要未经转换就把 Apple 地理编码坐标直接入库。

地点层级按「省 → 市 → 区县（可选）→ POI」维护。管理后台可自动识别并补建省市；新建省市要使用各自的行政中心坐标，**不能把酒店或景点的坐标复制给省市**，否则会影响足迹照片的位置匹配。地点有父级是正常的数据关系，不要把“江苏省 · 南通市”之类的路径写进视频标题；当前 iOS 视频页只需展示地点名和视频卡片。

## 5. 写入管理后台

1. 在「地点」页确认现有地点；不存在时新建，核对名称、层级、父级和高德选点坐标。
2. 打开该地点的「外链」页，选择 `BILIBILI` 或 `DOUYIN`，填写纯文本标题、标准视频地址、平台作者昵称、已验证的封面 HTTPS 地址。
3. 选择内容标签：能执行路线/费用/交通等信息选「实用攻略」；第一人称旅行或沉浸影像选「旅行记录」；侧重历史、人文、地理解释选「深度讲解」；确实不属这三类选「其他」。内容看不清时不要猜标签，先待核实。
4. 同地点有多条视频时设置非负整数排序；默认 `0`，相同时按创建时间排序。保存前再次检查视频 ID 和地点。

批量操作可走管理 API，但应先读取当前部署配置确认管理 API 地址与凭证，不能复用记忆中的旧地址。管理接口需要管理员令牌；脚本不要打印令牌或使用会输出请求头的 `curl -v`。当前接口契约如下：

| 操作 | 接口 | 关键字段 |
| --- | --- | --- |
| 查地点与标签 | `GET /places`, `GET /admin/link-tags` | 复用地点 ID；取得已有标签的 `tagId` |
| 建地点 | `POST /admin/places` | `name`, `level`, `lat`, `lng`, `parentId` 或 `ancestors` |
| 修正地点 | `PATCH /admin/places/:id` | 名称、层级、坐标、父级等需要修正的字段 |
| 建外链 | `POST /admin/places/:id/links` | `platform`, `title`, `url`, `creatorName`, `thumbnailUrl`, `sortOrder`, `tagId` |
| 修正外链 | `PATCH /admin/links/:id` | 仅传需要修改的字段 |
| 删除失效外链 | `DELETE /admin/links/:id` | 删除前确认链接确实失效或关联错误 |
| 查重与复查 | `GET /admin/links`, `GET /admin/places/:id/links` | 管理端需要令牌 |
| 公开验证 | `GET /places/:id`, `GET /places/pins` | 检查实际下发给客户端的数据 |

管理 API 要求外链地址和封面地址为 HTTPS；标题最多 100 字、作者最多 100 字、视频 URL 最多 500 字、封面 URL 最多 1000 字。`tagId` 是标签 ID，不是标签名称。校验允许作者、封面和标签为空；本流程的发布标准更严格。错误数据优先用 `PATCH` 修正，别通过再建一条来“覆盖”。视频失效或位置明显错误时在核实后删除外链；地点删除没有对应的日常管理接口，错误地点要单独确认是否有关联内容再处理。

## 6. 发布后复查

每批入库完成后逐条检查：

- 公开 `GET /places/:id` 的 `name`、`ancestors`、`lat/lng`、`links` 与预期相符；视频 ID、平台、标题、作者、封面都正确。
- `GET /places/pins` 中目标地点 `linkCount > 0`，地图上能找到；无视频地点不会显示在「知」地图。
- 封面 URL 仍返回图片，标题没有 `<em`、`</em>`、`&amp;` 或其他搜索/HTML 残留；全量管理外链中没有同 ID 重复项。
- 在手机上点开目标地点，确认卡片有真实封面和作者；点击抖音标准地址时优先进入抖音 App，哔哩哔哩链接打开目标视频。数据修正后退出该地点再进入即可重新拉取；只有改了客户端界面才需要重新构建和安装。

最后向用户汇报已入库的视频及地点、待核实项和失效/404 项，分别说明数量和原因。批量账号分析需要同时报告主页作品数与实际检查数；没有逐条检查到的作品不能计入“已完成”。
